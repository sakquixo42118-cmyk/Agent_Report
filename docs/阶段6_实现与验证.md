# 阶段6：任务账本与执行统计

版本：0.2.0-alpha.6；日期：2026-11-09；分支：feature/planning-agent；接在阶段5提交0ee13b0之后。此轮完成统计基础，课后主动检查/催办与运行期间提醒留给下一阶段。

## 1. 使用入口

重新构建并正常重开应用后，侧栏显示“v0.2 α6 · 执行回顾”。点击“统计”查看近7日完成、计划基线、主动推迟与耗时误差；可选择历史截止日。记录启用前显示未启用，不用最终任务状态倒推旧历史。

- 新版每个日期第一次确认执行计划后，自动冻结当时该日待办任务集合。未来日期也可在首次确认时建立基线；每次同批确认的该日任务一起纳入，不是逐块冻结。
- 升级前已有的今日计划可在统计页点“冻结已有今日计划”。只捕获操作当时仍待完成且有执行块的任务，不重建过去，也不包含冻结前已完成任务。没有已保存待办计划就不能冻结。
- 之后增加任务单列，移出或归档不缩小冻结分母。基线条目保留冻结时的名称、时段、截止与原始估时。界面状态按当前有效记录回看，不是任意历史时刻的数据库复原。
- 日程和今日助理的计划确认卡，在存在实际改期时可选择原因。默认“未说明原因”；只有用户明确选“我主动推迟”且执行开始时间后移，才记为主动延期。原因不由模型自动填写。
- 完成任务后沿用已有耗时反馈入口。后补或更正的有效反馈会重新计算对应完成日的误差统计。

统计页还展示逐日核对与最近40条操作摘要。今日Agent新增只读get_statistics工具，可根据真实数据回答统计问题；它不能冻结基线、更改原因或直接写统计数字。

## 2. 各数字怎么算

| 指标 | 口径 |
|---|---|
| 选中日冻结计划完成率 | 已有效完成的基线任务数 / 冻结任务数；无基线显示未知。冻结后提前完成未来计划也视为目标已满足，趋势仍记在真实完成日 |
| 近7日完成任务 | 统计期内有效完成记录的唯一taskId数量；逐日图按完成时保存的本地日期分组，同一任务同日只计一次 |
| 按时完成率 | 完成当时已确认真实截止、且完成时间不晚于该截止的记录数 / 有确认截止的有效完成记录数；无截止/未确认截止不进该分母 |
| 主动推迟次数 | 用户明确选择主动推迟、且开始时间后移的执行改期事件数；重复确认不增计 |
| 主动推迟任务比例 | 期间至少主动推迟一次的唯一任务数 / 期间确认过执行安排的任务与期间冻结基线任务的并集数量 |
| 其他手动改期 | 手动确认的改期中，除上述postponed事件外的次数 |
| 助理建议后确认 | 经Agent计划卡确认的改期次数；可以包含用户标明的主动推迟，不能与主动推迟次数相加 |
| 系统自动改期 | actor=system的执行改期记录；当前没有系统自动提交排班服务，因此不能把助理建议后确认冒充系统自动改期 |
| 原始估时MAPE | 有效样本的平均abs(实际分钟－原始分钟)/原始分钟×100% |
| 计划时长MAPE | 有效样本的平均abs(实际分钟－当次预留分钟)/当次预留分钟×100%；未排班完成时用完成快照中的建议时长 |
| 平均绝对误差 | 有效样本的平均abs(实际分钟－原始分钟)，单位分钟 |

有效耗时样本要求：本版启用后有有效完成记录、实际耗时为正、原始/计划时长为正、没有明确中断或任务范围变化。缺实际耗时的记录排除。分组同时区分估时分组和user/model/rule来源，不把校准系数反复乘进统计。

完成时保存截止/估时/日期快照，后续改任务截止不改旧完成的按时判断。撤销完成使其统计记录失效；再次完成是新周期。归档已完成任务保留已发生的统计事实，但沿用原规则将它移出后续个人校准样本。两个用途分别使用stats_valid和原valid，避免删除卡片就把历史表现抹掉。

未启用、未冻结与无样本是不同情况。none表示记录启用前，partial表示统计在当天中途启用，full表示该日已启用；partial不表示有部分计划，更不表示部分冻结。只看baseline是否存在来判断计划完成率能否计算。

## 3. 数据实现与原子性

迁移v11新增statistics_meta、audit_context、task_events、day_plan_snapshots、day_plan_items；为completion_events增加统计追踪/有效性、完成时本地日/时区及截止快照字段。旧完成记录stats_tracked默认0，不拿任务当前截止补成历史快照。已有数据库仍先生成一致性备份。

task_events记录事项创建、内容/分类/标签/评分/估时/日期变更、完成/撤销/归档，以及执行块新增/改期/移除的前后摘要、actor、source、reason和来源指针。任务文本摘要最多500字，完整任务/录入原文仍在原表；它不是所有历史全文的版本库。完成反馈沿用completion_feedback的最新有效记录与更新时间，不假称保留了每一版反馈全文。

任务字段由SQLite触发器统一记录，直接SQL也不能绕过“写任务同时写账本”；withAudit在短事务内指定可信来源并在结束后恢复上下文。手工、自动分析、已确认助理方案和录入草案来源分开。作业模块应复用现有服务/草案桥接，或在同步withAudit中写领域数据，不把网络请求放进事务。

执行块由规划提交服务记录：previewId+taskId幂等键、改期前后时间和用户原因与计划一起保存。首次确认冻结基线也在同一事务内；账本、计划或基线任一步失败，全部回滚。新计划确认是用户操作，即使由模型提出，也不会将actor误标为system。旧planning_events、completion_events等领域记录仍保留，用于各自功能。

统计读取纯只读，按时间索引查询；不给模型整份原始流水，仅返回摘要、口径和来源引用。UI过去日期展示的是当前有效记录的回顾：撤销会修正历史计数，后补反馈会更新历史误差；不宣称提供当时界面状态的时间旅行查询。

## 4. 接口与协作

- main/statistics/ledger.ts：withAudit、validatePlanAudit、recordPlanEvent。
- main/statistics/service.ts：readStatistics、frozenPlan、freezeDay。
- shared/statistics.ts：统计DTO、用户改期原因和IPC常量。
- window.api.statisticsRead(endDate)：返回以选中日为截止的7日统计。
- window.api.statisticsFreeze(date)：手动捕获已有今日计划；不允许回填过去。
- planningCommit(previewId,audit?)、agentConfirm(runId,accepted,version?,audit?)新增可选PlanAuditInput；旧调用仍兼容。
- 确认处理器可接收可选第三参数planAudit；该参数来自可信UI确认路径，不写在模型可调用工具的Schema里。PendingChange和复习草案v1结构未改。

当前迁移号v11；罗德金新增作业表时先协商下一编号。真实作业/OCR未包含在本阶段。

## 5. 验证记录

新增25项隔离场景，连同阶段1—5的102项，共127项：v10迁移不造历史；不同来源/空修改；草案唯一创建；账本失败与上下文恢复；首次确认与重复提交；后加、移出、归档；完成撤销重做；提前完成/午夜；未知基线/样本；启用前日期；截止快照与边界；主动延期原因/唯一任务数；助理确认归属；无变化重排；计划/基线/账本回滚；有效样本手算与分组；缺耗时/中断/范围变化；只读与40条限制；工具读取统计；可信确认原因传递与模型参数拒绝。

真实千问新增统计问答案例：独立合成记录为近7日完成1项、原始MAPE50%、今日未冻结。断言真实调用get_statistics，完整回答上述事实，不能把未冻结说成0%/100%，也不能把coverage误读成部分计划；查询不产生任务/基线写入。

本轮先发现真实模型把partial误解为“有部分计划”，补充了工具返回定义和系统提示；保留事实断言后重新验证。最终完整`npm test -- --live`通过140项（127隔离＋13真实调用）；`npm run typecheck`、构建通过。`--statistics-live`仅跑本阶段真实案例并保留全部隔离测试。测试结果不代表模型首次成功率或误差校准一定带来提升。

界面验收使用独立临时库和合成案例：基线3项，完成1项，另1项移出、1项归档，后加完成1项；页面显示计划完成率33.3%、完成任务2项、主动推迟任务比例25%（1/4），2条有效样本的原始/计划MAPE均25%、平均绝对误差15分钟，分组分别50%和0%。逐日记录、基线状态与源数据手算一致；重开独立窗口后基线和反馈仍保留。

额外通过界面把一条11月10日未来安排改到11月11日：确认卡默认未说明原因，手动选“我主动推迟”后保存，列表显示新时段；直接只读核对合成库得到kind=postponed、actor=user、source=manual、reason=user_postpone且只有一次有效改期。实测期间发现Vue响应式对象无法直接跨IPC克隆，已将日程和今日助理两处确认参数都改为普通字段对象，重新构建并实际点击保存通过；首次失败未改变原计划。合成数据与验证文件不提交仓库。
