# 阶段5 补充：扫描件识别（OCR）

> 目标：让没有文字层的 PDF（拍照/扫描的教材、试卷）也能进入"考点分析 → 任务草案 → 试排"的同一条链路。

## 1. 为什么不是"读文字"，而是"看图"

文字版 PDF 里每个字都带坐标，pdfjs 直接抽出来即可。扫描件整页是一张图，**文字层为空**，任何"提高抽取阈值"的做法都拿不到内容，只能把页面画成图片再识别。

因此流程多两步：

```
PDF 页 --pdfjs--> 画布 --@napi-rs/canvas--> PNG --视觉模型--> 文本 --> 现有下游
```

## 2. 技术选型（均为实测结论，非推测）

| 环节 | 选择 | 实测结论 |
|---|---|---|
| 页面渲染 | `@napi-rs/canvas` 1.1.0 | N-API 预编译二进制，**不需要按 Electron ABI 重编译**（与 better-sqlite3 不同）；A4 页 2 倍渲染得 1224×1584 PNG，约 40KB |
| 文字识别 | 视觉模型（多模态） | `deepseek-flash`（V4.1-Flash）官方标注支持图片输入；`deepseek-v4-pro` 是纯文本，不能用于此路径 |
| 图片传参 | base64 data URL | 官方文档支持 `image_url` 内联 base64，单请求体上限 48MiB，单图 32MiB，单页远低于上限 |
| 本地 OCR | 未采用 | tesseract 对中文教材与数学公式效果明显弱于视觉模型，且需额外下载 15MB+ 语言包 |

**模型名提示**：`deepseek-chat` 已于 2026-07-24 退出官方模型列表。若设置里仍填旧名，建议改为 `deepseek-flash`。识别失败若提示"模型可能不支持图片输入"，先检查这一项。

## 2.1 必须传 `wasmUrl`（务必保留）

pdfjs v6 把 **JPEG2000(JPX)** 与 **JBIG2** 解码器改成了 WebAssembly。真实扫描件（尤其是中文教材、黑白扫描）大量使用这两种编码，**不传 `wasmUrl` 时解码会失败，整页被画成纯白**，OCR 拿到空白图，最终报"没有识别出任何文字"——看起来像文件没内容，实际是解码器没起来。

同一份 JPX 样本的实测对比：

| 场景 | 渲染墨迹比例 |
|---|---|
| 不传 `wasmUrl` | **0.0000**（整页空白） |
| 传 `wasmUrl` | **0.9989**（正常解码） |

传的是**文件系统路径且必须以 `/` 结尾**（Node 侧用 `fs.readFile` 读取，不是 fetch；不以斜杠结尾会被 `getFactoryUrlProp` 直接拒绝）：

```
wasmUrl = <pdfjs-dist>/wasm/
iccUrl  = <pdfjs-dist>/iccs/     # 可选，CMYK 图像色彩更准
```

回归用例 `JPEG2000 扫描件能解码渲染（守护 wasmUrl）` 用真实 JPX 样本渲染并断言墨迹比例 > 0.5，专门守这条——因为这类故障是静默的，不会抛异常。

## 3. 数据模型（v11）

只加列与加表，**不重建** `study_documents`，避免动到已有五个子表的外键。

```sql
ALTER TABLE study_documents ADD COLUMN ocr_state TEXT NOT NULL DEFAULT 'none';
-- none | needed | done | failed

CREATE TABLE study_pages (            -- 识别结果，按页存，主键 (doc_id,page_no)
  doc_id, page_no, text, source('text'|'ocr'), engine, ink_ratio, latency_ms, created_at
);
CREATE TABLE study_ocr_runs (         -- 每次识别的批次记录，便于排查与统计
  id, doc_id, from_page, to_page, status, model, prompt_version,
  total_pages, done_pages, error, created_at, finished_at
);
```

`study_pages` 是这套设计的关键：**识别结果按页落库**，带来三个性质。

1. 重复分析不再重复付费（命中即跳过）；
2. 中途取消或崩溃，已完成的页保留，下次续跑；
3. 文件内容变化（指纹不同）时整份清空，避免张冠李戴。

## 4. 状态流转

```
选文件 → registered → parseDocument
                        ├─ 有文字层 → parsed (ocr_state=none)
                        └─ 无文字层 → failed (ocr_state=needed)  ← 界面出现识别卡片
                                        ↓ 用户确认页码范围
                                    ocrDocument
                                        ├─ 有正文 → parsed (ocr_state=done)
                                        └─ 全空白/全失败 → failed (ocr_state=failed，可重试)
```

`status='failed'` 在"待识别"阶段的含义是"当前没有可分析文本"，不是"文件有问题"；界面据 `ocr_state` 显示为待识别卡片，不显示为错误。

## 5. 成本与安全边界

| 约束 | 取值 | 理由 |
|---|---|---|
| 单次页数上限 | 200 | 防止误选整本教材后长时间占用 |
| 并发页数 | 3 | 过高易触发限流，过低整份太慢 |
| 渲染倍率 | 2 | 小字与公式可辨，体积可控 |
| 单页超时 | 90 秒 | 视觉转录通常 3–15 秒 |
| 空白页 | 不调用模型 | 墨迹比例 < 0.05% 直接记空串，省一次调用 |
| 默认范围 | 前 30 页 | 先小步验证质量，再放大 |

**模型调用是可花钱操作，因此必须由用户点按钮触发**：选完扫描件只出现卡片与页码输入，不自动开跑。

## 8. 已知限制

- **不支持 `.docx` 内的图片**：Word 里的扫描图不会被识别，只有 PDF 走这条路；
- **识别质量取决于拍摄/扫描清晰度**：歪斜、阴影、低分辨率会显著降低准确率，暂无自动纠偏；
- **每页一次调用**：一本 300 页扫描教材约 300 次调用，耗时可观，因此默认只排前 30 页；
- **未接入 Agent 工具**：目前只能由界面按钮触发，模型无法在对话中自行发起识别（下一步可作为 `study_ocr` 工具接入，并前置"将识别 N 页"的确认卡）；
- **未做表格还原**：表格会被压平成文本行，跨页表格可能错位。

## 9. 故障复盘：显示「331 页 / 0 字」且不再提供识别入口

**现象**：教材《工科数学分析（下册）》解析出 331 页 / 0 字，既没有识别卡片，也拿不到正文。

**成因是一条链，不是单点**：

1. 修复 `wasmUrl` 之前的那次识别，30 页全部渲染成白页 → 墨迹 0 → 按设计不发模型 → 每页仍写入一条空记录的 `study_pages` 行；
2. 当时"是否识别成功"按**行数**判定，30 行 > 0，于是 `ocr_state` 被写成 `done`、`status=parsed`；
3. 再次解析时，"已识别页数"同样按行数统计，`keepOcr` 成立，于是保留 `done`；
4. 界面只在 `ocr_state === 'needed'` 时弹识别卡片 → 入口消失，只剩"已解析 0 字"。

于是**一次失败被永久记成了成功**，且失败证据（空页）反过来阻止了重试。

**修复（三层同时收紧）**：

| 位置 | 改动 |
|---|---|
| `study/ocr.ts` | 缓存只认 `TRIM(text) <> ''` 的页；空页永远重试，不会挡住再识别 |
| `study/documents.ts` | `keepOcr` 只按"有文字的页"计数；空记录存在也照常回到 `needed` + `failed` |
| `AgentChat.vue` | 入口不再只看 `ocrState`，改为 `ext === 'pdf' && pageCount > 0 && charCount === 0` 也弹卡片 |

**验证（真实文件，非构造样本）**：同一份 331 页 PDF，解析得到 `status=failed / ocr=needed`；用桩转录器识别第 5–7 页，三页 PNG 分别 197K / 384K / 150K、墨迹 0.040 / 0.057 / 0.102，落库后二次识别三页全部跳过。说明渲染、入库、缓存三层都正常，之前拿不到文字纯粹是 `wasmUrl` + 状态误判的叠加。

**教训**：判定"完成"必须看**产物是否非空**，不能看"有没有执行过"。凡是可能产出空值的批处理，都要把空产物当作未完成。

### 9.1 后续：只识别了前 30 页，却显示"已解析 331 页"

识别成功后界面报的是"331 页 / 23,597 字"，实际上只有 1–30 页有文字（库中 `study_pages` 30 行）。
`StudyDocument` 增加了派生字段 `recognizedPages`（按 `TRIM(text) <> ''` 统计），用于区分三种状态：

| 状态 | 判定 | 界面文案 |
|---|---|---|
| 无文字 | `ocr_state=needed` 或 `char_count=0` | "没有文字层（331 页），可识别" |
| 部分识别 | `ocr_state=done` 且 `0 < recognizedPages < pageCount` | "已识别 30/331 页，其余页仍无文字，可继续识别" |
| 整本完成 | `recognizedPages = pageCount` | "已解析 331 页 / M 字" |

部分识别时识别卡片会保留，起始页自动跳到我已识别的下一页，不必重新选文件。

## 10. 模型读不到教材：工具接入

**现象**：问"根据教材分析考点"，助理回答"我没有教材内容，也没有 OCR 工具"。

原因不是解析失败，而是**解析结果只存在库里，没有任何工具能让模型读到**；系统提示里还写着"没有真实作业解题或OCR工具"，
等于主动告诉模型它读不了。

### 10.1 让文字层也进 `study_pages`

原先只有 OCR 结果落 `study_pages`，文字版 PDF/DOCX/TXT 只记了页数与字数，正文仍留在原文件里。
现在 `parseDocument` 会把抽出的每页正文以 `source='text'` 落库，与 OCR 共用一张表。好处是三件事统一了：

- 模型读取只查一张表，不必每次重新解析原文件；
- "已解析了多少页"和"已识别多少页"是同一个口径（`recognizedPages`）；
- 换文件内容时清理逻辑只需维护一处。

### 10.2 两个只读工具

| 工具 | 作用 | 关键约束 |
|---|---|---|
| `get_study_documents` | 列出资料、总页数、已读页数、字数 | 没有可读正文时返回 hint，说明需用户点「识别文字」 |
| `read_study_pages` | 按页码读正文，带页标记 | 单次 ≤12 页且 ≤5000 字符；被截断时给 `nextPage`；无正文返回 `NO_TEXT` 而不是空结果 |

`NO_TEXT` 是刻意设计成**失败**的：返回空数组会让模型倾向于"这段没内容"，从而编造。明确报错才能逼它去请用户识别。

### 10.3 系统提示带上下文

`runner.instructions()` 追加一行当前可读教材（名称、总页、可读页），避免模型在调用工具前就断言"没有资料"。
同时把原来"没有真实作业解题或OCR工具"的说明改为"可读已解析正文，但不能自己发起 OCR 或解题"。

## 11. "模型工具调用格式无效"：校验器把可用响应丢掉了

**现象**：问"根据教材分析考点，安排学习计划"，先成功执行 4 次工具（查资料、读 1–12 页、读 10–14 页、查日历），
第 5 轮直接报"模型工具调用格式无效"，整轮作废。

### 11.1 三层原因

1. `model.ts` 的校验把 `tool_calls.length > 4`、id 缺失/重复、`arguments` 为对象等都判为整条响应非法。
   这些都是**可修复的差异**，却让整轮对话失败，且错误信息不含任何字段级线索。
2. `create_task_draft` **一次只加一条候选**。整份复习计划要十几条，而 `drive()` 一轮最多 8 次模型决策，
   模型读完资料只剩 4 轮 —— 它只能改用并行调用，而并行调用又正好被第 1 条规则拒掉。两者互为死结。
3. `max_tokens: 1800`。批量草案或长答复在这个上限下容易被截断，截断后的 JSON 参数无法解析。

### 11.2 改动

| 位置 | 改动 |
|---|---|
| `src/main/agent/model.ts` | 新增 `normalizeModelMessage()`：对象参数自动 `JSON.stringify`、缺 id 补编号、重复 id 去重、坏条目跳过、调用个数不再作合法性判据；不可用时错误信息带原因（含输出被截断的专门提示）；`max_tokens` 1800 → 4000 |
| `src/main/agent/draftTools.ts` | 新增 `create_task_drafts`（1—12 条一次提交），保留原 `create_task_draft` 兼容单条场景 |
| `src/main/drafts/service.ts` | 新增 `addItems()`：一次事务内去重后统一写入，全部重复时不产生新版本（避免版本空转导致用户手里的卡片失效） |
| `src/main/agent/bootstrap.ts` / `runner.ts` | 提示词明确：三条及以上用批量工具，逐条调用会耗尽轮次预算 |

## 12. "fetch failed"：请求根本没有发出去

**现象**：问"分析考点并制定一个月的复习计划"，界面直接显示 `fetch failed`，一条工具记录都没有。

### 12.1 定位过程

库里两次失败的时间戳都是发出请求后 **约 10.7 秒**结束。10 秒正是 Node 内置 fetch（undici）的默认连接超时，
说明 TCP 连接从未建立，与模型、提示词、工具协议都无关。本机实测：

```
curl https://api.deepseek.com/        → Connection timed out after 12010 ms（connect=0）
nslookup api.deepseek.com             → 198.18.0.145
```

`198.18.0.0/15` 是 Clash/Surge 等工具 fake-IP 模式分配的保留地址。
即：代理仍占着 DNS 解析，但 Node 的 fetch **不读取系统代理**，请求被送到一个只有代理才能接住的地址，于是挂到连接超时。
这也解释了为什么 21:15 之前同样的代码是通的——那次代理还在生效。

### 12.2 改动

| 位置 | 改动 |
|---|---|
| `src/main/ai/http.ts`（新增） | `rawFetch()` 走 Electron 的 `net.fetch`（Chromium 网络栈，**遵循系统代理**），不可用时回退 Node fetch；`withDeadline()` 保证超时必定结束等待，不依赖实现是否响应 AbortSignal；`fetchFailureText()` 解析 `cause` 上的 `ETIMEDOUT`/`ECONNRESET`/`ENOTFOUND` 等真实原因；`isRetryableFetchError()` 区分抖动与用户取消 |
| `src/main/agent/model.ts` | 改用 `rawFetch`，连接抖动与 429/5xx 各重试一次；单次上限 30s → 60s（批量草案要生成到 4000 token） |
| `src/main/ai/client.ts` | 同样改走 `rawFetch`，报错文案统一 |
| `src/main/agent/runner.ts` | 单轮总上限 120s → 240s，容纳一次重试 |

```
net.fetch 失败（8050ms）：模型响应超时（8 秒），已停止等待。若反复出现，请确认网络或代理是否可用…
```

重点不是这句话本身，而是**它按时结束了**：改造前同样的场景会一直挂着，界面永远"运行中"。

### 12.4 仍需用户侧确认

网络是环境问题，代码只能让其**正确报错并适配代理**。若代理处于「系统代理」模式，改造后即可连通；
若代理已关闭或仅剩 fake-IP DNS，需要用户开启代理 / 切换 TUN / 更换网络。
